## 三、问题清单

### 🔴 问题 1（P0）：真实自然语言提问全链路失败，前端永久停在「进行中」

- **现象**：在对话页输入任意真实业务问题（如「华东上个月 GMV 是多少？」），七步进度条推进到「SQL 生成」后**永久停在进行中**，且**「提问」按钮永久 `disabled`**、修正提示永久残留，用户既无法继续提问、也看不到「本步失败」的状态。
- **所属模块**：ChatBI（`sql_gen` + `pipeline` + 前端 `runStore` / `StepProgress` / `RunBanner`）
- **复现步骤（真实浏览器点按）**：
  1. 打开 `http://127.0.0.1:5173/`，以 `admin/admin123` 登录（真实输入 + 真实点击「登录」）；
  2. 在输入框输入「华东上个月GMV多少」，真实点击「提问」；
  3. 观察进度条：意图理解 ✅ 0ms → Schema 链接 ✅ 39ms → SQL 生成 ✅ 1.49s → **SQL 校验 「进行中」（等待 33s 无变化）**。
- **预期结果**：`sql_gen` 生成合规 SQL → 通过护栏 → 执行 → 出图 + 结论；或失败时**步骤徽标应变为「失败」，并释放「提问」按钮**。
- **实际结果（33s 后终态快照，逐字采集）**：
  ```
  main 文本：
  对话 / 提问 / 引用了未登记的物理表：['dwd_order_detail'] / SQL_TABLE_NOT_ALLOWED / 完成 / 意图理解 / 0ms /
  完成 / Schema 链接 / 39ms / 完成 / SQL 生成 / 1.49s / 【进行中】/ SQL 校验 / 待处理 / SQL 执行 /
  待处理 / 可视化编排 / 待处理 / 结论解读 / SQL 有误，正在修正…（第 2 次）/ SQL_TABLE_NOT_ALLOWED · 引用了未登记的物理表：['dwd…'] / 查看 SQL
  仍 disabled 的按钮：提问
  hint 区：正在修正…（第 2 次）
  ```
  SSE 侧确认流水线在 `sql_guard` 连续 3 次拒绝后**已发出终态**：
  ```json
  event: run.error
  data: {"code":"SQL_TABLE_NOT_ALLOWED","message":"引用了未登记的物理表：['dwd_order_detail']","retryable":false}
  event: run.finished
  data: {"status":"failed","steps_run":["intent","schema_link","sql_gen","sql_guard", ...],"retries":2}
  ```
  **精确结论**：`RunBanner` 顶部**确实显示了 `run.error`**（`SQL_TABLE_NOT_ALLOWED` + 错误消息），即"完全无任何提示"的说法不准确；但 ① `StepProgress` 的「SQL 校验」徽标**永久停在「进行中」**（应为「失败」），② 「提问」按钮**永久 `disabled`**（点击触发 TimeoutError：`<button disabled>`），③ hint 区**永久残留「正在修正…（第 2 次）」**。三者叠加使页面处于"看得见错误、但操作已死锁"的半崩溃态。
- **根因分析（两条独立缺陷）**：
  1. **LLM 生成违规 SQL**：真实 deepseek 模型连续生成 `fact_sales`→`orders`→`order_info` 等**未登记物理表**。护栏正确拦截，但重生成**不收敛**——每次尝试换一个错表名。
  2. **重生成丢上下文**：`SqlGeneratorAgent._build_retry_messages()`（`agents/sql_gen.py:126`）在重试时**只发送「失败 SQL + 错误」，丢弃了首轮的 `schema_prompt`（含「可访问表清单」）**。模型在重试时失去表清单约束，只能继续臆造表名 → 必然失败。
  3. **前端未反映终态**：`runStore.ts` 的 `run.finished` 分支只设置顶层 `status:'done'`，**不清除各步 `steps[step].status`**；`run.error` 只设顶层 error。而 `StepProgress` 的徽标由 `steps[step].status` 驱动，故残留 `running`。同时 `RunBanner` 对 `status==='error'` 不渲染任何状态徽标。
- **影响**：**核心业务「问一句 → 出一屏」在真实模型下 100% 失败**，为本次联调最高优先级问题。

### 🔴 问题 2（P0）：观测总览页 JS 崩溃，无法渲染

- **现象**：进入 `/observability` 后页面白屏/停在「加载中…」，控制台抛 React 异常。
- **所属模块**：前端 Observability（`OverviewPage`）
- **复现步骤（真实浏览器点按）**：登录后**真实点击顶部导航「观测」**（`link "观测" [ref=e8]`），URL 变为 `/observability`。
- **预期结果**：渲染 4 张 KPI 卡 + Top Agent + 平台自身成本。
- **实际结果**：
  1. `document.querySelector('main')?.innerText` 长度为 **0**（`"EMPTY"`）——整页完全空白；
  2. 控制台抛
     ```
     Error: Objects are not valid as a React child
     (found: object with keys {value, label}).
     ```
     （后续还有 `{value}` 变体，说明 `running_now` / `silent_failures` 等多个 KPI 字段均踩同一坑）
  3. **【本轮新发现·更严重】崩溃后整个 SPA 交互死锁**：该异常**未被任何 error boundary 捕获**，抛在应用根部导致整棵组件树卸载。此后所有 `snapshot` 均抓不到任何导航链接（`navref` 全部返回空），后续点击「FinOps」「对话」等导航**全部失效**，`location.pathname` 永久冻结在 `/observability`，必须手动刷新/重开页面才能恢复。即：**一次误入观测页 = 整个应用不可用**。
- **根因**：后端 `GET /obs/overview` 返回的 `kpi_cards.running_now` 是**对象** `{"value":0,"label":"当前运行中 Run"}`（`observability/service.py:245`），而前端 `OverviewPage.tsx:17` 直接传整个对象：
  ```tsx
  <StatCard label="正在运行" value={kpi?.running_now ?? 0} />
  ```
  React 无法把对象作为子节点渲染 → 崩溃。（`cost_today_micro` 等虽也是对象，但被 `formatNumber` 处理过则安全；`running_now`/`silent_failures` 未取 `.value`。）
- **修复方向**：① 取 `kpi?.running_now?.value`（及同类字段）；或统一后端 `kpi_cards` 契约（全部裸标量或全部带 label）；② **补一个顶层 Error Boundary**，使单页崩溃不再拖垮整个应用。
- **影响**：观测模块首屏完全不可用，且**因缺少 error boundary，崩溃会传染为全站不可用**——严重级别实际高于原评估。

### 🟠 问题 3（P1）：Run 详情接口恒返回空对象，详情页卡死

- **现象**：点击 Runs 列表任一记录进入 `/observability/runs/{trace_id}`，页面永久「加载中…」。
- **所属模块**：后端 API（`observability.py` / `chatbi.py`）
- **复现步骤**：
  1. `GET /api/v1/obs/runs?limit=1` 取一个 trace_id（如 `81f4f3103ef64d088ba40c6427bb7a29`）；
  2. `GET /api/v1/obs/runs/81f4f3103ef64d088ba40c6427bb7a29` → 返回 `{}`；
  3. 同 trace 在 `/chat/runs/{trace_id}` 亦返回 `{}`。
- **预期结果**：返回该 Run 的 span 树（`run_doc`）。
- **实际结果**：HTTP 200 + 空 body `{}`。
- **根因**：源数据**确实存在**（MongoDB `run_doc` 集合中该 trace 有 8 个 span），但接口调用的是 `metering.get_run_doc(trace_id)` —— **`OutboxMeteringService` 上根本不存在此方法**（仅 `record_*`）。正确取数入口应为 `repos.run_doc.get(trace_id)`（`storage/mongo/repo.py:166`）。该 `AttributeError` 被接口内 `except Exception` 静默吞掉，返回 `{}`。
- **验证**：`hasattr(OutboxMeteringService, 'get_run_doc')` → `False`。
- **影响**：Run 详情（可观测性核心下钻页）完全不可用；且异常被静默掩盖，无日志告警。

### 🟠 问题 4（P1）：护栏函数名报错信息失真

- **现象**：`sql_guard` 报「使用了白名单外的函数」，但列举的函数名在 SQL 中根本不存在。
- **所属模块**：ChatBI 护栏（`guard` 函数白名单校验）
- **复现步骤**：提交「华东上个月 GMV 是多少？」触发首次 `sql_guard`。
- **预期结果**：错误信息应指出 SQL 中**实际存在**的违规函数名（如 `DATE_FORMAT`/`DATE_SUB`，若确为白名单外）。
- **实际结果**：
  ```json
  {"code":"SQL_FUNCTION_NOT_ALLOWED",
   "message":"使用了白名单外的函数：['TIME_TO_STR', 'TS_OR_DS_TO_TIMESTAMP']"}
  ```
  而该 SQL 实际只含 `SELECT/SUM/DATE_FORMAT/DATE_SUB/CURDATE`。
- **根因**：sqlglot 解析后函数节点被**规范化/内部转换**（`TIME_TO_STR`、`TS_OR_DS_TO_TIMESTAMP` 是 sqlglot 的规范化名），报错时直接使用了规范化名而非用户 SQL 中的原名，导致信息不可读、无法据此修正。
- **影响**：误导用户与自愈重生成（问题 1 的重试也基于此错误信息，进一步降低收敛概率）。

### 🟡 问题 5（P2）：`/auth/me` 的 `username` 字段错误（返回 user_id）

- **现象**：以 `admin` 登录后，`GET /auth/me` 返回 `"username": "1"`；以 `analyst1` 登录返回 `"username": "2"`。
- **所属模块**：后端鉴权（`api/deps.py`）
- **复现步骤**：登录 → `GET /api/v1/auth/me -H "Authorization: Bearer <token>"`。
- **预期结果**：`"username": "admin"` / `"username": "analyst1"`。
- **实际结果**：返回数字 user_id 字符串。
- **根因**：JWT 仅携带 `sub`（= user_id），`deps.py:152-153` 构造 Principal 时 `username=sub`，未回查真实用户名。
- **影响**：任何以 username 为键的前端展示/逻辑会出错。

## 六、遗留问题与建议

1. **【阻断级】** 问题 1：真实模型路径不可用。建议：
   - 修复 `_build_retry_messages`：重试时**保留 `schema_prompt`（可访问表清单）**，仅追加失败信息；
   - 前端 `run.finished`/`run.error` 分支需将未完成步骤置为 `failed`（清掉 `steps[step].status='running'`），并在终态**释放「提问」按钮**、清除「正在修正…」hint。
2. **【阻断级】** 问题 2：`OverviewPage` 取 `.value`（或统一 `kpi_cards` 契约）；**并新增顶层 Error Boundary**，防止单页崩溃传染全站。

4. **【高】** 问题 4：护栏报错改用 SQL 中的原始函数名（可用 sqlglot 的原始文本/`sql()` 还原）。

6. **【中】** 问题 7/8：修正 ES audit 索引 mapping 或增补 `method` 字段；修正 `budget_usage` upsert 为真正的 `INSERT ... ON DUPLICATE KEY UPDATE`。
7. **【低】** 问题 9：失败 Run 补记 `error_code`。
8. **未覆盖项（受限于无成功数据）**：`visual` / `narrator` 步骤的正常路径、大屏 `publish`/`export`、预算 `POST`/`PATCH` 写入、价格 `sync`、成本 `recompute`、推荐 apply/reject —— 因问题 1 导致无成功 Run 数据，这些依赖真实运行数据的写流程未能端到端验证，建议在问题 1 修复后回归。

## 七、总体结论

- **基础设施与鉴权层**：健康。外部组件全连通，鉴权/越权/参数校验分支表现正确，错误码规范。
- **ChatBI 主链路**：**不通**。demo 录播可跑通，但真实 LLM 提问因「重生成丢表清单 + 前端不反映终态」而 100% 失败；错误虽在 `RunBanner` 可见，但步骤徽标与「提问」按钮**永久死锁**。
- **Observability**：**首屏不可用**（问题 2，且崩溃传染全站），Run 详情不可用（问题 3），其余页（Runs/Anomalies/Topology）正常。
- **FinOps**：**页面基本可用**，读写接口正常；存在用量重复键写入的底层问题（问题 8）。
- **横切**：审计全量落库失败（问题 7）、缺 Error Boundary（问题 2 传染）、若干 `except Exception` 吞错导致故障静默（问题 3/7/8/9）。

**优先级排序**：问题 2（全站传染）≈ 问题 1（核心链路死锁）＞ 问题 3 ≈ 问题 4（高）＞ 问题 5/6（中）＞ 问题 7/8/9（低）。
