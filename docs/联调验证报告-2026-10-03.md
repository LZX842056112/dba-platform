## 四、问题清单

### 🔴 问题 1（P0·启动阻塞）：未提交改动导致后端无法启动

- **现象**：`uvicorn dba.main:app` 在 **import 阶段**即抛 `FastAPIError`，后端完全起不来（不是某接口不可用）。
- **所属模块**：API 接入层（`api/v1/finops.py`）
- **复现步骤**：在工作区未提交状态下执行 `python -m uvicorn dba.main:app`，或 `python -c "import dba.main"`。
- **预期结果**：应用正常导入并启动。
- **实际结果**：
  ```
  fastapi.exceptions.FastAPIError: Invalid args for response field!
  Hint: check that dict[str, typing.Any] | starlette.responses.JSONResponse is a valid Pydantic field type
  ```
  报错定位 `finops.py:198 @router.patch("/budgets/{budget_id}")`。
- **根因**：未提交改动把该路由返回注解从 `dict[str, Any]` 改为 `dict[str, Any] | JSONResponse`，
  但**未同步加 `response_model=None`**（同文件其余 11 个同类路由都有）。FastAPI 0.142 尝试把联合类型
  推断为响应模型 → 导入期失败。
- **影响**：**整个后端不可用**（P0）。HEAD 版本注解为 `dict[str, Any]`，本问题由未提交改动引入。
- **建议**：为该路由补 `response_model=None`（一行，与其余同类路由一致）；并在 CI 增加「应用可导入」的冒烟用例。

---

### 🔴 问题 2（P1）：Redis 不可用 → 限流中间件未 fail-open，业务接口全站 500

- **现象**：把 Redis 指向不可达地址后，除探针外的**所有业务接口返回 500**。
- **所属模块**：L1 接入层（`api/middleware.py` `RateLimitMiddleware`）
- **复现步骤**：`DBA_REDIS_DSN=redis://127.0.0.1:6399/0` 启动后端 → `GET /api/v1/finops/budgets`、`GET /api/v1/obs/overview`。
- **预期结果**：按 §7.6 与 P1-9「Redis 故障 fail-open」，降级放行（200）或明确降级，不得 500。
- **实际结果**：两者均 **500**；后端日志为 `redis.exceptions.ConnectionError ... 127.0.0.1:6399`，
  调用栈为 `RateLimitMiddleware.dispatch → RedisRateLimiter.allow → eval_via_lua`。
- **根因**：`TraceMiddleware`、`AuditMiddleware` 都做了 fail-open，**唯独 `RateLimitMiddleware` 未包 try/except**；
  且容器在 Redis「可构造但不可连接」时仍装配了 Redis 限流器。
- **影响**：Redis 抖动/重启即全站不可用，与文档承诺矛盾；现有回归用例
  （`test_api_middleware_failopen.py`）只注入 progress/audit 故障，**覆盖不到限流器**。
- **建议**：限流器失败按策略降级（建议 fail-open 并计一条自监控指标）；补一条「限流器抛错时业务请求不 500」的回归用例。

### 🟠 问题 3（P1）：FinOps 写接口无入参校验，错名/缺字段返回 500

- **现象**：`POST /finops/budgets`、`POST /finops/prices` 传入错误字段名或缺必填字段时返回 **500**，
  而非 400 参数校验失败。
- **所属模块**：FinOps API（`api/v1/finops.py`）
- **复现步骤**：
  ```
  POST /api/v1/finops/budgets  {"scope_type":"GLOBAL","bogus_field":1}      → 500
  POST /api/v1/finops/prices   {"provider":"e2e","bogus":1}                  → 500
  ```
- **预期结果**：400 + 字段定位（与读接口的缺参行为一致）。
- **实际结果**：500 `{"code":"50000","message":"预算写入失败"}` / `"价格写入失败"`；
  日志为 `Unconsumed column names: ...` / `'scope_id'`（SQLAlchemy 直接把 dict 灌进模型）。
- **根因**：两个写接口直接把请求体 dict 透传给 `repo.upsert()`，**没有 Pydantic 请求模型**；
  字段契约（`amount_micro_usd` / `soft_limit_pct` / `billing_unit` / `input_price_micro_usd` …）
  只存在于 `storage/mysql/models.py`，接口层无任何声明与校验。
- **影响**：外部调用方无法从接口契约得知正确字段，误用即 500；错误信息不回传，排障成本高。
- **补充**：**用正确字段调用时接口工作正常**（预算创建 200、修改版本 +1、价格创建 200），故属输入校验缺失而非功能不可用。
- **建议**：为两个写接口补 Pydantic 请求模型（含必填/枚举/范围校验），错误统一走 400 分支。

### 🟠 问题 4（P2）：`/auth/me` 的 `username` 返回 user_id（上一轮问题 5，未修复）

- **现象**：以 `admin` 登录后 `GET /api/v1/auth/me` 返回 `"username": "1"`。
- **所属模块**：鉴权（`api/deps.py` → `Principal`）
- **复现步骤**：登录 → `GET /api/v1/auth/me`。
- **预期结果**：`"username": "admin"`。
- **实际结果**：`"1"`（JWT 的 `sub` 即 user_id，构造 Principal 时未回查真实用户名）。
- **影响**：任何以 username 为键的展示/逻辑会出错。
- **建议**：Principal 构造时按 `sub` 回查用户名（或把 username 写入 JWT claim）。

- **现象**：会话列表每条记录含 `"_id": "6abf..."`。

### 🟠 问题 6（P2）：失败 Run 的 `error_code` 恒为 null（上一轮问题 9，未修复）

- **现象**：`GET /api/v1/obs/runs` 中 `status=failed` 的记录 `error_code` 全为 `null`（实测 **0/36**）。
- **所属模块**：埋点 / Run 汇总
- **预期结果**：失败 Run 记录失败分类（如 `SQL_TABLE_NOT_ALLOWED`）。
- **实际结果**：`error_code: null`；而 SSE 的 `run.error` 明确携带 `code`。
- **影响**：观测侧无法按错误类型统计失败分布。
- **建议**：`run.error` 终态回填 `error_code` 到 run 汇总行。

### 🟡 问题 7（P2）：记忆指标读取失败，接口恒返回 0 值

- **现象**：后端日志反复 `记忆命中率读取失败（降级）：'float' object is not callable`；
  `GET /api/v1/obs/metrics/memory` 返回 `{"hit_rate":0.0,"lookups":0,"hits":0,"series":[]}`。
- **所属模块**：Observability（记忆指标读取）
- **复现步骤**：调用 `GET /api/v1/obs/metrics/memory`，观察后端 warning。
- **预期结果**：返回真实命中率/查询量。
- **实际结果**：因类型错误（把 float 当函数调用）恒走降级分支，指标恒为 0。
- **影响**：记忆维度观测数据不可用；因 fail-open 静默，容易被忽略。
- **建议**：修正该读取路径的类型处理，并让降级在响应中显式标注（`degraded: true`）。

### 🟡 问题 8（P3）：`budget_usage` 主键冲突（上一轮问题 8，未修复）

- **现象**：日志持续 `Duplicate entry '1-2026-10-01' for key 'budget_usage.PRIMARY'`（本轮 9~23 次/实例）。
- **所属模块**：FinOps 预算 / MySQL
- **预期结果**：用量 upsert 幂等（`INSERT ... ON DUPLICATE KEY UPDATE`）。
- **实际结果**：同 `(budget_id, period_date)` 重复 insert，冲突被吞掉。
- **影响**：冲突那次写入被丢弃，用量统计可能偏小。
- **建议**：改为真正的 upsert（或先 SELECT 再 UPDATE）。

### 🟡 问题 9（P3）：AgentToken 仅校验存在性，不校验取值

- **现象**：`POST /obs/otel/v1/traces`、`POST /obs/agents/register` 只要带**任意非空** `X-Agent-Token` 即 200。
- **所属模块**：Observability 接入（`_require_agent_token`）
- **复现步骤**：`POST /api/v1/obs/agents/register` + `X-Agent-Token: e2e-arbitrary-token` → 200。
- **预期结果**：与共享密钥比对，不匹配应 401。
- **实际结果**：仅判空。
- **影响**：任意调用方可注册 Agent 并向观测侧灌入数据（数据完整性风险）。
- **建议**：接入共享密钥（配置项 + 常量时间比较）。

---

### 🟡 问题 10（P3）：观测 / FinOps 子页面无导航入口

- **现象**：顶栏仅「对话 / 观测 / FinOps」三个入口；`/observability/runs|topology|anomalies`、
  `/finops/budgets|reuse|recommendations` **在页面上没有任何链接**，只能手输 URL 直达。
- **所属模块**：前端路由 / 导航（`app/App.tsx`）
- **复现步骤**：登录后点「观测」，检查 `document.querySelectorAll('a[href^="/observability/"]').length` → `0`。
- **预期结果**：二级导航或页面内入口。
- **实际结果**：无入口（本轮 UI 走查全部通过 URL 直达完成）。
- **影响**：7 个页面实际上「不可发现」，功能可点性打折。

---

### 🟡 问题 11（P3）：`/ready` 语义与探针覆盖范围

- **现象**：MySQL（读写 + 只读）全不可达时 `/ready` 返回 **200 degraded**（`mysql.ok=false`），非 503。
- **所属模块**：运维端点（`main.py`）+ 健康探针
- **实际结果**：`hard_down = all(...)` —— 仅当 mysql/mongodb/redis **全部**不可用才 503。
- **影响**：① 单个硬依赖挂掉时 K8s readiness 不会摘除实例，写路径已断却仍判就绪；
  ② `mysql` 探针走**只读**连接池，只覆盖 `DBA_MYSQL_RO_DSN`（本轮实测：只坏读写 DSN 时 `/ready` 仍报 `mysql ok`）。
- **建议**：明确 readiness 语义（硬依赖任一不可用即 not_ready），并让 mysql 探针同时覆盖读写连接。

---

### 🟡 问题 12（P3）：`query` 不校验 session 存在性与归属

- **现象**：`POST /api/v1/chat/sessions/any/query` 用不存在的 session_id 也能 200 并启动 Run。
- **所属模块**：ChatBI API
- **实际结果**：返回 `trace_id` + ticket，Run 正常执行（不泄露他人数据，但会污染会话归属）。
- **建议**：校验 session 存在且属于当前用户，否则 404。

---

### ⚪ 观察项（非缺陷）：SSE 回放窗口对超长 Run 的挤压

- **现象**：一次 Run 产生 4986 帧（`narration.delta` 1218+ 条），**回放窗口仅保留最近 200 条**，
  导致 `run.started` 等早期事件在订阅时已被挤出，无法回放。
- **影响**：断线重连时早期事件不可见（终态仍在，续传语义未破坏）。
- **建议**：或提高窗口/TTL，或对高频 `narration.delta` 做聚合后再入回放队列。

## 七、总体结论

### 7.1 各流程与分支覆盖情况

- **ChatBI**：七步主链路 + 6 类护栏拒绝分支 + 自愈重生成 + 行级权限（fail-closed 与真实注入双向）+ 取消 + SSE +会话生命周期
  **全部覆盖**；其中护栏拒绝与自愈分支借助脚本化 LLM 在**真实 HTTP + SSE + 真实数据库**下确定性复现。
- **Observability**：5 页 + 12 个接口 + 异常闭环**全覆盖**；上一轮崩溃与详情空数据已修复。
- **FinOps**：4 页 + 22 个接口（含 8 个写接口）**全覆盖**；读写功能正常，输入校验缺失。
- **跨模块**：同一 `trace_id` 在观测/成本侧的可见性与一致性**已验证**。
- **故障降级**：MySQL 不可用表现符合设计；Redis 不可用**不符合**文档承诺（问题 2）。降级态前端表现合格。
